# 需求与技术方案评审 Skill

## 目标

对需求文档和技术方案文档（MD 格式）进行专业评审，从多个维度发现潜在问题，生成结构化评审报告，用于需求评审会议、技术方案评审会议或文档完善。

## 输入输出

- **输入**：需求/技术方案文档 Markdown 文件路径（支持单个文件或多个文件/目录）
  - **单文件**：直接评审该 MD 文件
  - **多文件**：自动扫描目录下所有 `.md` 文件，合并后统一评审
  - **目录**：自动扫描目录下所有 `.md` 文件，按修改时间排序后合并
- **输出**：评审报告 Markdown 文件，输出到主 MD 文件所在目录
  - `<MD文件名>_评审报告.md` — 评审报告

## ⚠️ 图片和附件解析要求

**评审必须包含对文档中引用的图片和附件的分析！**

### 图片解析

需求文档和技术方案中的图片通常包含关键信息：

| 图片类型 | 关键内容 | 评审要点 |
|---------|---------|---------|
| **业务流程图** | 流程节点、分支条件、异常处理 | 流程完整性、分支覆盖、循环/死锁检查 |
| **页面流转图** | 页面跳转、状态变化 | 状态流转完整性、跳转条件清晰 |
| **状态机图** | 状态定义、触发条件、流转规则 | 状态闭环、非法流转检查 |
| **架构图** | 系统分层、模块划分、依赖关系 | 分层合理性、模块边界清晰 |
| **时序图** | 接口调用顺序、数据流转 | 调用顺序合理、异常处理 |
| **UI 原型图** | 页面布局、交互元素 | 功能覆盖、交互合理性 |
| **数据模型图** | 表关系、字段定义 | 关系正确、字段完整 |

### 附件解析

附件通常包含补充说明：

| 附件类型 | 关键内容 | 评审要点 |
|---------|---------|---------|
| **接口文档 PDF** | 接口定义、参数说明 | 与正文描述一致性 |
| **协议模板 DOCX** | 协议内容、签署要求 | 协议完整性、合规检查 |
| **数据字典 XLSX** | 字段定义、枚举值 | 字段覆盖、命名规范 |

### 解析步骤（必须执行）

1. **扫描图片目录**：检查 MD 文件所在目录下的 `images/` 子目录
2. **识别图片引用**：从 MD 内容中提取所有 `![]()` 图片引用
3. **逐一读取图片**：使用 read_file 工具读取每张图片内容
4. **分析图片内容**：识别图片类型，提取关键信息用于评审

### 模型不支持图片时的处理

**如当前模型不支持图片输入（read_file 返回 unsupported image 错误），必须：**

1. **明确提示用户**：
   ```
   ⚠️ 当前模型不支持图片输入，无法解析文档中的流程图等关键图片内容。
   
   建议更换为支持多模态的模型版本，或手动提供图片关键内容描述。
   
   未解析的图片清单：
   - images/额度测算_004.png (业务流程图)
   - images/额度测算_005.png (页面流转图)
   ```

2. **列出未解析图片清单**：包括文件名、引用位置、预估内容类型

3. **建议更换模型**：提示用户切换到支持多模态的模型版本（如 qwen-vl、gpt-4-vision 等）

4. **提供备选方案**：
   - 用户手动描述图片关键内容
   - 使用 OCR 工具提取图片文字
   - 暂停评审等待模型更换

## 文档类型识别

根据文档内容自动识别文档类型：

| 类型 | 判断依据 | 评审侧重 |
|------|---------|---------|
| **需求文档** | 包含「需求背景」「功能描述」「用户故事」「验收标准」等章节 | 需求评审维度 |
| **技术方案** | 包含「设计目标」「核心流程」「表设计」「接口设计」「技术选型」等章节 | 技术方案评审维度 |
| **混合文档** | 同时包含需求和设计内容 | 全维度评审 |

## 评审维度

### 一、需求评审维度

#### 1. 需求疑问（Questions）

从以下角度识别需求中的疑问点：

| 检查项 | 说明 | 示例 |
|--------|------|------|
| **业务逻辑不清** | 业务流程、规则描述不明确 | "客户完成签约后自动发起测额"——什么条件下触发？ |
| **边界条件缺失** | 未说明边界情况处理方式 | 接口超时时间未定义、重试次数未说明 |
| **责任边界模糊** | 各系统/模块的职责划分不清 | "雨商返回结果"——失败时由谁处理？ |
| **数据流转不明** | 数据如何在系统间传递未说明 | 征信数据如何存储、传输加密方式 |
| **异常处理缺失** | 异常场景下的处理逻辑未定义 | 授权过期、接口失败、数据异常 |

#### 2. 模糊点（Ambiguities）

识别需求描述中模糊、可多义理解的地方：

| 检查项 | 说明 | 示例 |
|--------|------|------|
| **用词模糊** | 使用"可能"、"大概"、"适当"等不确定词汇 | "适当时候展示结果"——具体时机？ |
| **量化指标缺失** | 缺少具体数值、阈值 | "快速返回结果"——多快算快速？ |
| **条件不完整** | if-else 分支描述不全 | "如果成功则... "——失败呢？ |
| **时间定义模糊** | 时间点、时效性不明确 | "及时通知用户"——多长时间内？ |
| **范围定义不清** | 功能适用范围、用户范围未界定 | "部分客户可见"——哪些客户？ |

#### 3. 与历史逻辑冲突点（Conflicts with Historical Logic）

对比分析新需求与现有/历史业务逻辑的冲突：

| 检查项 | 说明 | 示例 |
|--------|------|------|
| **流程冲突** | 新流程与现有流程矛盾 | 现有流程先签约后授权，新需求反过来 |
| **状态冲突** | 状态定义或流转规则冲突 | 现有状态机无"测额中"状态，新需求新增 |
| **数据冲突** | 数据字段、格式、规则变更 | 原接口返回字符串，新需求改为对象 |
| **权限冲突** | 权限模型变化 | 原代理商可操作，新需求限制为管理员 |
| **兼容性冲突** | 新老版本兼容问题 | 新接口不兼容旧客户端版本 |

> **注意**：此维度为**可选检查项**。
> - **如用户提供历史需求文档**：对比新老需求差异，识别流程、状态、数据、权限等冲突点
> - **如未提供历史版本**：跳过显式对比，但基于文档内部描述推断可能存在的逻辑变更点，并在报告中标注"（推断，待确认）"

#### 4. 需求完整性检查（Completeness）

检查需求文档是否完整覆盖必要内容：

| 检查项 | 说明 |
|--------|------|
| **版本记录** | 是否有版本变更记录 |
| **需求背景** | 是否说明为什么做这个需求 |
| **功能描述** | 每个功能模块是否有详细描述 |
| **接口定义** | 涉及的接口是否有完整定义（入参、出参、异常） |
| **前端页面** | 是否有界面原型或页面调整说明 |
| **数据字典** | 新增/修改的数据字段是否有定义 |
| **埋点/监控** | 是否有埋点、监控、告警要求 |
| **安全合规** | 是否有安全、隐私、合规要求 |
| **回滚方案** | 是否有灰度发布、回滚策略 |
| **依赖项** | 是否列出上下游依赖系统 |

#### 5. 可测试性分析（Testability）

分析需求是否具备可测试性：

| 检查项 | 说明 | 示例 |
|--------|------|------|
| **验证标准明确** | 是否有明确的验收标准 | "提升用户体验"无法量化测试 |
| **测试数据可得** | 是否容易构造测试数据 | 需要第三方配合的数据难以测试 |
| **异常可模拟** | 异常场景是否可模拟测试 | 网络超时、接口报错是否可模拟 |
| **边界值可测** | 边界条件是否可测试 | 有效期15天的边界是否可测 |
| **性能指标可测** | 性能要求是否可量化测试 | 响应时间<2s 可测试 |

#### 6. 需求风险评估（Risks）

识别需求实施过程中的潜在风险：

| 检查项 | 说明 |
|--------|------|
| **第三方依赖风险** | 依赖外部系统/接口的稳定性 |
| **数据迁移风险** | 是否有历史数据需要迁移 |
| **上线风险** | 发布时对现有业务的影响 |
| **合规风险** | 是否涉及征信、隐私等合规要求 |
| **业务风险** | 需求理解偏差、业务逻辑漏洞 |

### 二、技术方案评审维度

#### 7. 架构设计评审（Architecture Design）

评审系统架构设计的合理性：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **分层设计** | 分层是否清晰、职责是否单一 | 表现层/业务层/数据层是否清晰分离 |
| **模块划分** | 模块边界是否清晰、耦合度 | 模块间是否存在循环依赖 |
| **服务拆分** | 服务粒度是否合理 | 是否过度拆分或单体臃肿 |
| **扩展点设计** | 是否预留扩展机制 | 策略模式、插件机制、配置化 |
| **依赖关系** | 依赖是否清晰、是否合理 | 是否存在不必要的强依赖 |

#### 8. 核心流程评审（Core Flow）

评审业务流程设计的合理性：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **流程完整性** | 主流程、分支流程是否完整 | 是否遗漏异常分支、回退流程 |
| **流程合理性** | 流程步骤是否必要、顺序是否合理 | 是否存在冗余步骤 |
| **状态流转** | 状态机设计是否合理 | 状态是否闭环、是否有非法流转 |
| **并发处理** | 并发场景是否有处理方案 | 分布式锁、乐观锁、幂等设计 |
| **事务设计** | 事务边界是否合理 | 分布式事务方案、事务补偿 |

#### 9. 数据库设计评审（Database Design）

评审数据库表结构设计：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **表结构设计** | 字段类型、长度是否合理 |金额字段是否用 Decimal、状态字段类型 |
| **主键设计** | 主键策略是否合理 | 自增ID vs UUID、分布式ID方案 |
| **索引设计** | 索引是否覆盖查询场景 | 是否有复合索引、是否冗余索引 |
| **字段命名** | 命名是否规范、是否易理解 | 是否遵循团队命名规范 |
| **必要字段** | 是否包含必要的基础字段 | created_at、updated_at、version 等 |
| **数据冗余** | 是否有不合理的数据冗余 | 冗余字段是否同步更新机制 |
| **分库分表** | 是否有分库分表需求及方案 | 数据量预估、分片键选择 |

#### 10. 接口设计评审（API Design）

评审 API 接口设计：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **命名规范** | 接口命名是否遵循规范 | RESTful 风格、动词/名词使用 |
| **参数设计** | 入参是否合理、是否必要 | 是否有必填/选填说明、参数校验 |
| **返回值设计** | 出参结构是否合理、是否完整 | 是否有统一返回格式、错误码定义 |
| **版本管理** | 是否有接口版本管理方案 | 版本号策略、兼容性处理 |
| **幂等设计** | 是否有幂等性设计 | 重复请求如何处理 |
| **限流设计** | 是否有接口限流方案 | 限流阈值、限流策略 |
| **文档完整性** | 接口文档是否完整 | Swagger/YAPI 文档是否齐全 |

#### 11. 技术选型评审（Technology Selection）

评审技术选型的合理性：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **框架选型** | 框架是否适合业务场景 | 是否过于复杂或功能不足 |
| **组件选型** | 第三方组件是否合理 | 是否成熟稳定、是否有替代方案 |
| **新技术引入** | 新技术引入是否必要 | 团队是否熟悉、是否有学习成本 |
| **技术栈统一** | 是否与现有技术栈一致 | 是否引入不兼容的技术 |

#### 12. 性能方案评审（Performance Design）

评审性能相关设计：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **性能指标** | 是否有明确的性能要求 | 响应时间、并发数、吞吐量 |
| **缓存方案** | 缓存策略是否合理 | 缓存粒度、过期策略、缓存穿透处理 |
| **异步处理** | 是否有异步处理方案 | MQ 使用、异步任务设计 |
| **批量处理** | 批量操作是否有优化 | 分页查询、批量写入 |
| **连接池配置** | 连接池参数是否合理 | 数据库/HTTP 连接池大小 |

#### 13. 安全方案评审（Security Design）

评审安全相关设计：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **数据安全** | 敏感数据是否有保护措施 | 加密存储、传输加密、脱敏展示 |
| **接口安全** | 是否有接口安全措施 | Token 校验、签名校验、防重放 |
| **权限控制** | 权限校验是否完整 | RBAC 设计、数据权限控制 |
| **日志安全** | 日志是否有脱敏处理 | 是否打印敏感信息 |
| **SQL注入防护** | 是否有 SQL 注入防护 | 是否使用参数化查询 |

#### 14. 可扩展性评审（Scalability）

评审系统的扩展能力：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **水平扩展** | 是否支持水平扩展 | 无状态设计、负载均衡 |
| **配置化程度** | 业务逻辑是否可配置 | 规则引擎、配置中心 |
| **插件化设计** | 是否有插件化机制 | 策略模式、SPI 机制 |
| **预留扩展点** | 是否预留扩展点 | 预留字段、扩展接口 |

#### 15. 可运维性评审（Operability）

评审系统的运维友好度：

| 检查项 | 说明 | 示例问题 |
|--------|------|---------|
| **监控告警** | 是否有完整的监控方案 | 业务监控、技术监控、告警阈值 |
| **日志规范** | 日志是否规范、可追踪 | TraceId、日志级别、关键节点日志 |
| **灰度发布** | 是否有灰度发布方案 | 灰度策略、回滚机制 |
| **配置管理** | 配置是否可动态调整 | 配置中心、热加载 |
| **故障恢复** | 是否有故障恢复方案 | 重试机制、熔断降级 |

#### 16. 技术风险评估（Technical Risks）

识别技术实现过程中的潜在风险：

| 检查项 | 说明 |
|--------|------|
| **技术难点** | 技术实现是否有难点、是否有解决方案 |
| **依赖风险** | 第三方依赖是否稳定、是否有备选方案 |
| **工期风险** | 开发工作量预估是否合理 |
| **人员风险** | 是否依赖特定人员、团队能力匹配 |
| **环境风险** | 测试环境、生产环境差异 |

## 处理流程

### AI 评审阶段（大模型执行）

**重要：评审报告由AI分析MD内容生成，而非脚本自动生成！**

AI 需以多角色视角进行评审：
- **需求评审**：产品经理 + 测试工程师视角
- **技术方案评审**：架构师 + 高级开发视角

#### 评审步骤：

**步骤 -1：读取知识库历史文档（新增）** ⭐

> ⚠️ **评审前必须读取知识库，对比历史需求发现冲突点！**

**-1.1 检查知识库是否存在**

```
检查 E:\效贷\.qwen\knowledge-base\ 目录是否存在
```

**-1.2 读取知识库索引**

```
读取 E:\效贷\.qwen\knowledge-base\INDEX.md
```

**-1.3 搜索相关历史文档**

根据以下维度搜索：
- **业务领域匹配**：当前需求属于「贸易融资」→ 搜索 requirements/ 下贸易融资类文档
- **功能相似匹配**：当前需求涉及「征信查询」→ 搜索包含征信功能的历史文档
- **关键词匹配**：当前需求名称关键词 → 搜索 INDEX.md 中的关键词

**-1.4 读取历史文档**

读取匹配到的历史文档（最多 3 份），提取：
- 历史需求中的业务规则
- 历史评审报告中的问题项（同类问题是否重复出现）
- 历史技术方案中的接口定义、状态定义

**-1.5 呈现知识库读取状态**

```markdown
## 📚 知识库读取状态

| 知识库内容 | 文档名称 | 读取状态 | 提取内容 |
|-----------|---------|---------|---------|
| 历史需求 | 额度测算.md | ✅ 已读取 | 征信查询流程、状态定义 |
| 历史评审报告 | 额度测算_评审报告.md | ✅ 已读取 | 征信接口超时未定义（同类问题） |
```

## 注意事项

1. **评审结果需人工审核确认**：AI 评审结果作为参考，需产品经理/架构师确认
2. **历史对比需明确版本**：如需对比历史需求，需明确指定历史文档路径
3. **严重级别定义**：
   - 🔴 **严重**：阻塞开发/上线，必须解决后才能继续
   - 🟡 **重要**：影响设计实现，建议评审会议讨论
   - 🟢 **一般**：优化建议，可后续完善
4. **结合业务知识**：AI 会基于文档内容进行推理，但可能不了解项目特定背景，需人工补充
5. **输出位置**：评审报告输出到被评审 MD 文件所在目录
6. **文档类型自动识别**：根据章节内容自动判断评审维度
