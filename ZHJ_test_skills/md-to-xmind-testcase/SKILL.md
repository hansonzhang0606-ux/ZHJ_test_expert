# Markdown 转 XMind 详细测试用例（整合分析版）

## 目标

整合分析**需求文档、需求评审报告、场景示例文件、技术方案文档**，从多维度提取测试用例，生成**详细测试用例 JSON + XMind** 文件用于评审。每个测试用例包含：用例名称（含优先级）、前置条件、测试步骤、预期结果。

## 输入输出

- **输入**：需求文档 Markdown 文件路径 + 评审报告 + 场景示例文件（如有）
- **输出**：
  - `<MD文件名>_测试用例_详细版_v1.0-ai.json`
  - `<MD文件名>_测试用例_详细版_v1.0-ai.xmind`

---

## ⚠️ 优先级分配规则（必须遵守）

### P0 占比控制

**P0 用例数量控制在总用例数的 10% 左右，P0 仅为主流程用例。**

| 优先级 | 占比 | 定义 | 示例 |
|-------|------|------|------|
| **P0** | ~10% | 核心主流程，不通过则阻塞上线 | 退款单作废正常流程、各设备端主功能验证 |
| **P1** | ~40% | 重要功能、场景示例验证、异常处理 | 场景示例1-6验证、库存不足拦截、满减分摊验证 |
| **P2** | ~40% | 边界条件、兼容性、次要功能 | 不同纸张类型、打印机兼容性、空值处理 |
| **P3** | ~10% | 极端场景、性能、安全 | 并发、特殊字符、极端长度 |

### P0 判定标准

P0 用例必须同时满足：
1. 覆盖**核心业务主流程**（非异常/边界）
2. 不通过会**阻塞核心功能使用**
3. 每个功能模块的**主入口操作**（如退款单作废的"点击作废→确认→数据恢复"完整流程）

### P0 过多时的处理

如果初始推导的 P0 用例超过 10%：
- 将"验证XX正确"类用例降级为 P1
- 将"XX展示正确"类用例降级为 P1
- 将"XX边界值"类用例降级为 P2
- 仅保留"XX主流程完整通过"类用例为 P0

## ⚠️ 场景示例文件处理规则

### 识别场景示例

需求文档或附件中可能包含场景示例文件（如 `场景示例.md`），这些文件提供了具体的业务场景数据和预期行为。

**必须将场景示例转化为测试用例！**

| 场景示例类型 | 转化方式 | 示例 |
|------------|---------|------|
| **带具体数值的场景** | 直接作为测试用例，前置条件写明具体数据 | "订单商品A销售价100元、成本价60元、退款金额100元" |
| **带计算过程的场景** | 前置条件写明输入值，预期结果写明计算结果 | "返还积分=2000*(24/80)=600积分" |
| **带分步骤的场景** | 每个步骤转化为测试步骤，每个结果转化为预期结果 | "退款时：库存+1→作废后：库存-1" |

### 场景示例用例结构

```
P0/P1: 示例X-场景名称
├── 前置条件: 具体业务数据（销售价XX元、成本价XX元、积分XX、储值XX元等）
├── 测试步骤: 1.操作前记录数据 2.执行操作 3.验证各维度数据变化
└── 预期结果: 退款时XX+1→作废后XX-1（逐维度列出）
```

## JSON 格式规范（必须匹配 generate_xmind.py 脚本）

**JSON 格式必须使用 `{title, modules, sub_modules, testpoints}` 结构，不支持 `children/tags/precondition/steps` 等字段。**

### 每个测试用例的结构

每个测试用例是一个 `sub_modules` 节点，下挂 3 个子节点：前置条件、测试步骤、预期结果：

```json
{
  "name": "P0: 用例名称",
  "sub_modules": [
    {"name": "前置条件", "testpoints": ["条件1", "条件2"]},
    {"name": "测试步骤", "testpoints": ["1.步骤1", "2.步骤2", "3.步骤3"]},
    {"name": "预期结果", "testpoints": ["结果1", "结果2"]}
  ]
}
```

### 完整 JSON 结构

```json
{
  "title": "版本号 测试用例",
  "modules": [
    {
      "name": "1.功能模块名称",
      "sub_modules": [
        {
          "name": "主流程",
          "sub_modules": [
            {
              "name": "P0: 用例名称",
              "sub_modules": [
                {"name": "前置条件", "testpoints": ["条件1"]},
                {"name": "测试步骤", "testpoints": ["1.步骤1", "2.步骤2"]},
                {"name": "预期结果", "testpoints": ["结果1", "结果2"]}
              ]
            }
          ]
        },
        {
          "name": "场景示例验证",
          "sub_modules": [
            {
              "name": "P1: 示例1-场景名称",
              "sub_modules": [
                {"name": "前置条件", "testpoints": ["具体业务数据"]},
                {"name": "测试步骤", "testpoints": ["1.操作前记录", "2.执行操作", "3.验证数据"]},
                {"name": "预期结果", "testpoints": ["操作前XX→操作后XX（逐维度列出）"]}
              ]
            }
          ]
        },
        {
          "name": "异常处理",
          "sub_modules": [
            {
              "name": "P1: 异常场景名称",
              "sub_modules": [
                {"name": "前置条件", "testpoints": ["异常条件"]},
                {"name": "测试步骤", "testpoints": ["1.触发异常操作"]},
                {"name": "预期结果", "testpoints": ["toast提示文案", "操作不执行"]}
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

### 优先级标注方式

优先级直接写在用例名称中：`P0: 用例名称`、`P1: 用例名称`、`P2: 用例名称`

### XMind 生成脚本

```bash
py -3 .qwen/skills/md-to-xmind-testcase/scripts/generate_xmind.py \
  --input <测试用例.json> \
  --output <输出.xmind>
```

### XMind 层级结构（脚本自动生成）

```
根节点：版本号 测试用例
├── 一级：功能模块
│   ├── 二级：用例分类（主流程/场景示例/异常处理/边界场景）
│   │   ├── 三级：P0/P1/P2: 用例名称
│   │   │   ├── 前置条件
│   │   │   │   ├── 条件1
│   │   │   │   └── 条件2
│   │   │   ├── 测试步骤
│   │   │   │   ├── 1.步骤1
│   │   │   │   └── 2.步骤2
│   │   │   └── 预期结果
│   │   │       ├── 结果1
│   │   │       └── 结果2
```

## 测试用例推导规则

### 一、从需求文档推导

| 维度 | 分析要点 |
|------|---------|
| **正常流程** | 主操作流程验证（P0） |
| **异常场景** | toast报错、拦截、不可操作 |
| **边界条件** | 最大值/最小值、刚好/超出 |
| **数据验证** | 各维度数据变化（库存/成本/销售额/毛利/收支/积分/储值） |
| **权限控制** | 有/无权限验证 |
| **UI验证** | 页面元素、交互操作 |
| **跨端验证** | PC/App/Pad端差异 |

### 二、从场景示例推导

场景示例是测试用例的**最佳来源**，因为需求文档已提供具体数值和预期行为：

1. 识别场景示例中的**具体数据**（销售价、成本价、积分、储值等）
2. 将数据写入**前置条件**
3. 将场景中的操作步骤转化为**测试步骤**
4. 将场景中的"退款时→作废后"对比转化为**预期结果**

### 三、从评审报告推导

将评审报告中的**疑问点、模糊点、风险点**转化为补充测试用例：

| 评审问题类型 | 转化方式 |
|------------|---------|
| 需求疑问 | 转化为功能验证用例（P1） |
| 模糊点 | 转化为边界/规则验证用例（P1/P2） |
| 历史逻辑冲突 | 转化为兼容性验证用例（P1） |
| 风险提示 | 转化为风险场景用例（P2） |

### ⚠️ 评审报告补充场景的处理规则

**评审报告中的疑问/模糊点/风险，必须结合用户的实际答复来决定是否生成用例，不能盲目全部转化为测试用例！**

| 用户答复类型 | 处理方式 | 示例 |
|------------|---------|------|
| **明确不存在此场景** | ❌ 不生成用例 | "退款单不支持组合支付，不存在此场景" → 移除组合支付退款单作废用例 |
| **概念已明确无需确认** | ❌ 不生成用例 | "在线收款和扫码收款是同一概念，无需确认" → 移除概念一致性确认用例 |
| **业务规则已明确** | ✅ 按答复生成用例 | "订单不支持多次退款，但作废后可再次发起部分或全部退款" → 生成"作废后可再次发起退款"用例 |
| **保留为待验证** | ✅ 生成用例 | "赊账订单退款单作废后未结清状态恢复逻辑未明确" → 生成验证用例 |
| **无明确答复** | ✅ 生成待确认用例（P2） | 评审报告中未得到答复的疑问 → 生成"待确认"用例 |

**处理流程**：
1. 逐条扫描评审报告中的疑问/模糊点/风险
2. 检查是否有用户的明确答复（在对话中或评审报告标注中）
3. 有答复的按答复处理（不生成/生成/调整）
4. 无答复的生成待确认用例（P2）

## 处理流程

### 步骤 1：读取所有关联文档

- 需求文档 MD
- 评审报告 MD
- 场景示例文件（如有）
- 技术方案文档（如有）

### 步骤 2：读取知识库测试模式

读取 `patterns/` 目录下：
- 通用测试模式.md
- 需求分析规则库.md
- 历史Bug预防清单.md

### 步骤 3：推导测试用例

1. 从需求文档推导：功能/异常/边界/UI/跨端
2. **从场景示例推导**：将每个场景转化为完整测试用例（前置条件+步骤+预期结果）
3. 从评审报告推导：疑问/模糊点/风险转化为验证用例
4. 从知识库补充：历史场景/测试模式/Bug预防

### 步骤 4：分配优先级

- P0：仅主流程，控制在 ~10%
- P1：场景示例验证、异常处理、重要功能
- P2：边界条件、兼容性、次要功能
- P3：极端场景

### 步骤 5：生成 JSON + XMind

按 JSON 格式规范生成，调用脚本生成 XMind。

### 步骤 6：自检

| 检查项 | 通过标准 |
|-------|---------|
| P0占比 | ≤15% |
| P0用例归属 | P0用例放在对应功能模块下，非集中在一个模块 |
| 场景示例覆盖 | 每个场景示例都有对应测试用例 |
| 前置条件 | 写明具体业务数据（数值、状态） |
| 测试步骤 | 可执行、步骤清晰 |
| 预期结果 | 可验证、结果明确 |
| toast文案 | 与需求文档完全一致 |
| 评审报告覆盖 | 疑问/模糊点/风险结合用户答复处理 |
| 评审补充场景 | 不存在场景/已明确概念的不生成用例 |

## 注意事项

1. **P0 控制在 10%**：P0 仅为主流程用例，不包含异常/边界
2. **场景示例必须转化**：需求文档中的场景示例是测试用例的最佳来源
3. **前置条件写明具体数据**：如"销售价100元、成本价60元、积分2000"，不要写"存在一笔订单"
4. **预期结果逐维度列出**：如"库存-1件、成本-60元、销售额+100元、毛利+40元"
5. **toast文案完全一致**：从需求文档中逐字复制toast提示文案
6. **JSON 格式匹配脚本**：必须使用 `{title, modules, sub_modules, testpoints}` 结构
7. **脚本路径**：`.qwen/skills/md-to-xmind-testcase/scripts/generate_xmind.py`
8. **不测历史功能**：历史需求文档仅用于理解背景，不推导测试用例
9. **不自行推断**：需求未明确时用"待确认"标注
10. **正常/异常成对覆盖**：生成正常路径后检查对应异常路径
11. **P0 用例必须放在对应功能模块下**：不能将所有 P0 集中在一个模块下，每个功能模块的主流程 P0 用例应放在该模块的分支下
12. **评审报告补充场景必须结合用户答复**：评审报告中的疑问/模糊点/风险不能盲目全部转化为用例，需结合用户的实际答复（如"不存在此场景""概念已明确无需确认"等）来决定是否生成用例
